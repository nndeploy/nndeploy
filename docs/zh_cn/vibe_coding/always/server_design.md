**nndeploy Server：完整需求与实施方案**

日期：2026-11-12。状态：待实施设计；已纳入单机多模型并行、入口队列隔离和设备资源约束。本文中的新增 Python 接口、HTTP 接口、配置字段和目录均为拟议方案，不代表当前代码已实现。之前撤销的代码不在本次文档变更中恢复。

**1. 目标与约束**

在现有 `python/nndeploy/server` 上形成完整的 AI HTTP Server。工作流编辑器、工作流 JSON、代码构建的 Graph、普通 Python 算法都使用同一套 Server、任务、Worker、文件和数据库能力。

统一约束：

- 公共模块仅使用 `nndeploy.server`，公共入口为 `Server`。不增加平行的入口包或公共执行框架。
- 对外计算调用使用 Deploy；启动、停止和重载使用 Start、Stop、Reload。
- 保留现有 Workflow、Graph、Node、Edge、Worker、Task、File。运行名称是 HTTP 路由键，不再形成一套发布业务对象。
- 不引入需要用户操作的 Artifact、Revision、Deployment、Alias、Contract。内部锁、校验摘要、文件引用和执行序号仍按正确性需要实现。
- 原始 `workflow.json` 的格式保持不变。附加配置采用 `workflow.server.json`；其他文件名使用 `<工作流文件名去掉扩展名>.server.json`，也允许显式指定路径。
- 算法专用代码留在算法目录下的 `server/`，公共设施留在 `nndeploy.server`。
- 完整功能通过少量公共入口使用；内部文件拆分依据职责，不要求用户创建内部组件。
- 默认 SQLite、本地文件、每入口的本地队列即可运行。MySQL、PostgreSQL、对象存储、Redis 按配置启用。
- 工作流和代码接入不因数据库、存储后端改变而修改计算逻辑。
- TaskQueue 共用实现，按对外入口隔离队列；模型之间默认不因同处一台机器或同一 Server 而串行。全局限额是总量约束，不是一条机器级 FIFO 队列。

完整范围包括单机和多个 Server/Worker 实例的显式部署。自动扩缩容、跨地域调度、任意代码热替换、通用 GPU 算子级抢占不属于本次范围。多实例能力不等于这些能力已经具备。

**4. 总体架构与依赖方向**

```text
编辑器 / 工作流 JSON / Graph / Python 代码 / 外部客户端
                         │
             Server（HTTP、校验、鉴权、按名称路由）
                         │
            ┌────────────┼────────────────┐
            ▼            ▼                ▼
         Queue A      Queue B          Queue C
            │            │                │
       Worker A     Worker B1/B2      Worker C
            │            │                │
         模型 A       工作流 B        算法自身调度
            │            │                │
            └────────────┼────────────────┘
                    结果、文件、事件

共享实现和设施：TaskQueue / DB / Storage / Redis / 日志 / 指标
资源限额：应用/入口/设备级准入；不默认建立整机串行执行队列
```

Server 负责请求、任务和资源；DAG 负责计算。`dag` 不依赖 FastAPI、数据库、Redis、用户身份或云厂商 SDK。

将现有 `NnDeployServer` 改造为可代码创建的 `Server`，旧名称和 CLI 保留兼容入口，不再增加套在它外面的完整 Server 实现。共享依赖保存在应用实例状态，通过 `dependencies.py` 获取，避免跨应用共享全局实例。

公共操作限定为添加执行入口、启动、停止、重载、查询、Deploy。注册表只是“名称 → 创建代码及能力说明”的映射，不记录发布历史。

一个 Server HTTP 应用可以有多个命名入口，每个入口关联工作流、Graph 或代码。隔离单位是这个入口，不是 Graph 中的每个模型节点；一个包含多个模型的 Graph 仍由 DAG 编排为一次任务。名称直接对应路由中的 `{name}`，不另外维护可变别名。编辑器默认使用工作流 ID 作为稳定名称，展示名称继续使用工作流名称；自定义名称必须在 Server 范围内唯一，冲突返回 409。

**5. 三种运行方式**

| 方式 | 行为 | 适用范围 |
| --- | --- | --- |
| 带编辑器的 Server | 同一应用挂载编辑器、工作流管理和 Deploy 路由 | 本地搭建、调试和小规模使用 |
| API-only Server | 启动同一套执行能力，仅挂载调用及授权管理接口 | 独立运行、生产部署 |
| 多实例 Server + Worker | 关系数据库、共享对象存储和 Redis 配合 | 多进程、多节点的显式部署 |

关闭带编辑器的整个 Server 会停止它拥有的 Worker。若需要关闭编辑器后台后仍可调用，使用单独启动的 API-only Server；编辑器通过受保护的管理接口提交已有工作流和配置。此时只有进程通信，不增加发布对象。

独立模式不依赖编辑器数据库中的 ID：它接受实际的工作流内容或受信任资源引用。编辑器 ID 只用于关联来源。跨主机启动时由现有文件接口上传缺失资源或引用共享 Storage，Server 取得本地可用文件后再加载；不能把编辑器机器的路径原样发给另一台机器使用。

多实例只支持具有共享语义的数据库和资源位置。不同机器不能把同一个本地绝对路径当作同一资源。SQLite + 本地目录的默认模式不宣称支持分布式 Worker。

同一机器运行多个模型时，分别处理以下情况：

| 场景 | 排队与执行归属 | 并行语义 |
| --- | --- | --- |
| 多个独立 Server 进程、不同端口 | 各进程独立队列及 Worker，默认独立运行目录 | 可以同时执行；不会自动发现彼此并排成一条队列 |
| 一个 Server 托管多个命名入口 | 每个入口独立队列，默认独立 Worker 或独立执行线程 | A 的长任务不阻止 B 派发；实际速度取决于硬件和算法 |
| 多个请求调用同一普通 Graph | 同一入口内排队，一个 Graph 实例默认一次一个请求 | 可用多个独立 Graph Worker 提高并行能力 |
| 入口使用支持多请求的算法引擎 | 外层限定在途数量，交给引擎自身调度 | 引擎可以执行连续批处理或 Token 级调度 |
| 多个 Server 显式组成同一组 | 使用相同的共享配置、DB/Storage 和 Redis 命名空间 | 同一入口的 Worker 消费该入口队列，不同入口保持隔离 |

只使用相同 Redis 地址或数据库地址不应意外合并任务域。独立部署需要不同命名空间和配置范围；同组部署需要明确一致的入口名称、权限与配置。共用数据库/schema 时持久化记录按配置范围隔离，文件对象前缀和 Redis key 使用相同范围。多个独立进程不能无保护地共享同一个本地运行目录。


**6. Python 接口与对象所有权**

以下为拟议接口。

```python
from nndeploy.server import Server

# 工作流文件
server = Server(workflow="workflow.json", config="workflow.server.json")
server.run(host="127.0.0.1", port=8000)
```

```python
# 已构建的、尚未初始化的 Graph；使用当前进程内的受控执行线程
server = Server(graph=graph, name="detect")
server.run(port=8000)
```

```python
# 原生进程隔离、多 Worker：在各 Worker 内创建 Graph
server = Server(graph_factory=build_graph, name="detect", workers=2)
server.run(port=8000)
```

```python
# 无状态函数
server = Server(deploy=my_deploy, name="detect",
                input_model=DetectRequest, output_model=DetectResponse)
server.run(port=8000)
```

```python
# 常驻模型，不要求继承框架基类
class TextDeploy:
    def init(self):
        self.model = load_model()

    def deploy(self, inputs):
        return {"text": self.model.generate(inputs["prompt"])}

    def deinit(self):
        self.model.close()

server = Server(handler_factory=TextDeploy, name="text",
                input_model=TextRequest, output_model=TextResponse)
server.run(port=8000)
```

单个 Server 托管多个模型的拟议代码：

```python
server = Server()
server.add(name="detect", graph_factory=build_detect_graph,
           config="detect.server.json")
server.add(name="ocr", graph_factory=build_ocr_graph,
           config="ocr.server.json")
server.add(name="chat", handler_factory=build_chat_handler,
           config="chat.server.json")
server.run(port=8000)
```

上述入口拥有各自的队列和运行参数。多个入口使用同一实例的 `add(name=..., workflow=.../graph_factory=.../deploy=...)`。`create_app()` 返回可挂载的 ASGI 应用，`run()` 负责独立启动。入口参数互斥，不能同时传入 workflow、graph 和 deploy。

所有权规则：

- 传入未初始化 Graph 后，其执行期间的初始化、运行和释放由 Server 独占管理，调用方不再并发操作它。
- 不静默迁移已经初始化的 Graph；首先拒绝并给出明确说明，或仅在后续实现验证过的显式接管方式下支持。
- 直接 Graph 对象或捕获不可序列化对象的函数不自动具备多进程能力。工厂函数/可导入入口用于进程隔离。
- 同步函数进入执行线程，异步函数使用所属 Worker 的事件循环；生成器和异步生成器按流式入口处理。
- 创建、初始化、执行、同步和释放保持资源所需的线程/进程归属。构造函数已创建 GPU 上下文的代码优先采用 Worker 内工厂。
- Python 调用通常在启动时固定；热重载 Python 模块通过重启对应 Worker 实现，不在正在执行的对象上替换类定义。
- 代码接口的 schema 由显式 Pydantic 模型或受支持的类型标注生成。无法推导时要求声明，不能猜测任意 Python 对象的结构。

**7. 编辑器操作与工作流接入**

界面入口为 `Server`，所有新增文案为英文。常用视图只展示 Inputs、Outputs、Parameters、Status、Endpoint、Start/Stop/Reload 和调用示例；高级配置折叠。

Start 的一次操作执行：

1. 使用现有保存逻辑保存画布；模板保存为用户工作流。
2. 取得这一次保存的确切内容，不在异步过程中反复读取可能被其他页面修改的文件。
3. 加载已有 `workflow.server.json`，或识别已知节点/公开端口并生成默认配置。
4. 检查配置、插件和资源；类型或映射有歧义时在页面指出具体节点/字段。
5. 准备当前运行所需的配置和资源，交给 Worker 初始化。
6. 只有初始化、绑定和配置的预热全部成功后才显示 Ready 和调用地址。

普通保存不修改在线 Graph；Reload 显式应用当前画布。页面自动显示当前入口，无需选择部署记录。调用示例始终来自正在运行的配置，不能被未启动的草稿改写。

后台在一次 Start/Reload 中完成校验和配置保存，不要求浏览器先调用多个检查/保存接口。HTTP 响应丢失时，浏览器保留操作标识并重试。编辑器用现有工作流的修改校验值检查并发编辑，冲突返回 409；校验值是内部一致性数据，不显示给用户管理。

原有 Run 仍执行一次性工作流，不自动变成常驻调用。Graph 内部并行配置保持原意：只有验证可重复、安全隔离的执行类型才开放给常驻 HTTP；不把所有 Graph 静默改成串行，也不宣称任意流水线都已支持。

**8. 配置格式与输入输出转换**

区分应用配置和工作流配置：`server.json` 控制 HTTP、DB、Storage、Redis、鉴权等环境设施；`workflow.server.json` 控制当前入口的输入输出、运行和资源策略。数据库和云凭据不进入工作流配置。

最小工作流配置：

```json
{
  "name": "image-copy",
  "inputs": {
    "image": {"node": ["decode"], "type": "image"}
  },
  "outputs": {
    "image": {"node": ["encode"], "type": "image"}
  }
}
```

映射规则：

- `node: ["subgraph", "decode"]` 使用真实节点路径，避免拼接字符串产生歧义。
- `edge: "image"` 引用 Graph 已公开的输入/输出边。内部边不能未经检查就当成外部端口。
- 已知输入输出节点由内部转换实现读写；配置不要求填写适配器名称。
- 多输入/多输出节点可用 `port` 指定端口；无法唯一识别时必须显式指定。
- `type` 描述 HTTP 数据类型，不替代节点的设备、布局、dtype 等计算类型信息。数组/Tensor 转换额外声明 dtype、shape/大小上限，校验后再分配内存。
- 参数可声明节点路径、已支持的参数名、类型、范围、required 和 default；不允许任意 setattr 或请求期间重新反序列化整个 Graph。
- 只有明确支持运行时修改的参数可以按请求变更；设备、权重和初始化参数通过 Reload 生效。
- 可选字段必须有明确定义的默认值，包括显式 null；每次请求应用默认值，不能继承上次请求。
- 拒绝未知字段、重复 JSON key、重复写入目标、非法类型和无法安全序列化的结果。
- 不明确公开的参数不允许客户端修改。对外 Deploy 请求不接受任意工作流或 Python 导入路径。

算法特定的预处理/后处理留在算法目录；通用 Base64、MIME、JSON、文件引用、图片/音频编码等放在 Server 的 `io.py` 和 `media.py`。

可选运行配置示例：

```json
{
  "name": "image-copy",
  "inputs": {"image": {"node": ["decode"], "type": "image"}},
  "outputs": {"image": {"node": ["encode"], "type": "image"}},
  "execution": {
    "workers": 1,
    "devices": ["cpu"],
    "scheduling": "serial",
    "max_concurrency_per_worker": 1,
    "max_queue_size": 32,
    "queue_timeout_seconds": 30,
    "execution_timeout_seconds": null,
    "restore_on_restart": true
  },
  "resources": {"mode": "managed"}
}
```

其中 workers、设备范围、队列容量、并发和期限均属于该入口，不是整台机器的设置。普通 Graph 默认 serial；concurrent 只用于声明可并发且通过验证的代码；engine 表示请求交给算法自身调度，外层仍执行校验和在途数量限制。配置与算法能力不相容时启动失败，不静默改变并发方式。

`devices` 是 Worker 允许使用的设备范围。实际 Graph/代码的设备配置必须与其一致，不能仅标注一个设备名就认定模型已迁移。多 Worker 的放置由显式参数或已声明的工厂能力决定；多卡模型由工厂声明完整设备组，Server 不把它拆成单卡实例。无法验证设备归属的自定义代码不能获得严格设备隔离承诺。

应用级配置示例，所有字段均为拟议格式：

```json
{
  "http": {"host": "127.0.0.1", "port": 8000, "editor": true},
  "database": {"url": "sqlite:///./resources/db/nndeploy.db"},
  "storage": {"backend": "local", "root": "./resources/files"},
  "redis": null,
  "limits": {
    "scope": "server",
    "max_pending_tasks": 256,
    "max_inflight_tasks": 8
  },
  "entries": {
    "detect": {"workflow": "detect.json", "config": "detect.server.json"},
    "ocr": {"workflow": "ocr.json", "config": "ocr.server.json"}
  }
}
```

应用级上限限制总量，不改变每个入口独立排队的结构。每入口和总量限额取同时满足的结果。多个进程若要共享总量限额，必须显式选择共享范围并使用跨进程协调；不能假定各自设置 8 就等价于整机最多 8。

应用配置优先级统一为：显式 Python 参数或 CLI > 环境变量 > 指定应用配置文件 > 默认值；工作流字段的显式覆盖同样校验并记录有效配置。秘密值不在有效配置查询和日志中原样返回。引用路径相对于配置所属目录解析，再接受资源根目录和权限校验。

**9. 执行、调度与任务语义**

对同步、异步和流式请求采用同一个 Task。已经接受的计算统一使用 `task_id` 关联结果、事件、文件和日志，不另建一套同义请求记录。HTTP 尝试可有 request_id 用于拒绝请求和传输诊断；它不成为另一套业务实体。对 API 暴露的小写状态与现有队列枚举建立显式映射，旧 `/api/queue` 响应保持原样。

任务状态沿用现有含义并补齐：pending、dispatched、running、succeeded、failed、cancelled、expired。取消请求先记录 cancel_requested，只有真正停止后才进入 cancelled。状态转换由条件更新保护，终态不能被迟到的进度覆盖。

排队和调度使用以下规则：

- 每个对外入口有独立的逻辑队列和执行名额。默认分配专属 Worker；直接 Graph 对象模式使用专属执行线程。同一入口多个 Worker 处理同一入口任务，不能误取其他模型的请求。
- 一个 Graph 实例默认串行执行请求。多个 Worker 创建独立实例，可能重复占用模型内存；扩大 Worker 数必须经过资源检查。
- 声明可并发的纯代码可以提高单 Worker 在途数量；依赖 Python CPU 密集代码的线程并发不承诺提高计算吞吐。
- LLM 等具有自身调度器的入口采用 engine 模式：外层负责校验、配额、任务记录和有界准入，把多个允许的请求交给引擎。不能设置一个等待前一请求完全结束的外层串行循环。
- 排队上限计入待派发及已派发未开始的任务，运行名额单独计数；不能转移到 multiprocessing.Queue 或引擎内部无界队列来绕过背压。引擎自身保留任务时必须提供容量或背压反馈。
- 一个入口队列满只拒绝该入口的新增请求；其他入口仍可接受任务，但仍受它们自己的限额和应用总量上限约束。若要求容量保证，可配置各入口的保留名额，避免一个入口用尽总量。
- 调度器只向有容量且设备匹配的 Worker 派发，不持有全局锁等待慢入口；共享资源时按公平策略选择可运行入口，优先级不得导致永久饥饿。
- Start/Stop/取消/心跳使用控制通道，不放在普通计算任务之后无限等待。重载、取消和故障恢复按入口作用域执行，不停止其他入口。

所谓全局限制必须注明范围：单个 Server 实例、显式组成的一组 Server，或同一主机上的指定设备。默认只提供实例及入口限额，不隐式控制其他独立进程。

设备资源规则：

1. 为 Worker 配置设备归属、CPU 线程限制、运行并发和可用时的内存预算。多个入口在同一 GPU 上可以同时运行，但速度、显存和引擎兼容性需要实际验证。
2. 模型加载和 Reload 先检查及预留资源；预热完成后保留必要运行余量。旧 Graph 在途任务未完成前，不把它的资源提前当作已释放。
3. 显存查询和配置预算只用于准入，不是硬件配额或确定性保证。非受管进程可能继续占用显存；OOM 必须按入口失败处理，不能声称已完全避免。
4. 独立 Server 若需同机协调，显式加入共享协调范围，设备键包含主机标识及稳定设备标识。控制范围仅覆盖参与者；不会自动控制机器上的其他进程。
5. 协调者失联或租约过期不代表原生计算结束，不得立刻释放执行名额并允许超额任务启动；先确认进程结束或将设备标为待核实。恢复后对账。
6. 默认不抢占、自动卸载或关闭其他入口以给新模型让路。资源不足返回明确错误；需要停机重载时由用户显式选择。
7. 共享 Worker 或 GPU 共享是显式优化，需说明故障及性能影响范围。请求与队列隔离不等于显存、算力或故障的物理隔离。

显式批量调用定义逐条结果和整体错误。动态合批仅对声明能力的同一入口启用，按形状/参数兼容分组，遵守最大批量和最大等待时间，拆分结果保留原 task_id。不同模型、不同配置或不兼容身份隔离要求的请求不混成一批。算法自身已进行批处理时，外层默认不再次动态合批。

三个不同期限：

- 排队期限：开始执行前已过期，记录 expired，绝不再运行 Graph。
- 执行期限：先协作取消；需要硬终止时结束隔离 Worker，并记录受影响任务。
- HTTP 等待期限：连接结束不代表原生计算结束；保留任务和资源，按 disconnect 策略继续或请求取消。

直接 Graph 对象的线程模式不能承诺硬终止原生计算。要求硬期限的入口必须使用进程隔离。结束一个共享 Worker 会影响它的其他任务；需要独立故障范围时使用独占 Worker。

请求结束前分离可变输出，恢复动态参数和请求路径，释放临时对象。原生执行失败、同步失败或无法恢复的状态污染后，关闭对应 Graph，下次按配置重建；不把校验失败等普通请求错误当作模型损坏。

**10. 流式输出与事件**

保留现有任务日志/进度机制，统一事件为 start、progress、delta、result、error、done，包含 task_id 和单调事件序号。算法协议可以转换这些事件为其要求的外部格式。

节点运行百分比属于 progress，Token、音频片段等属于 delta；必须由算法或节点实际输出，不能用进度伪装增量结果。SSE 开始发送后不能再改变 HTTP 状态码，因此错误通过 error 和最终状态事件表达。

网络发送与计算之间使用有界缓冲。慢客户端触发背压、断连或可重放缓冲策略，禁止无限累积。长连接有心跳、空闲超时、权限检查和连接数限制。

断线续传只有在事件保留启用时提供，使用事件序号或 Last-Event-ID；超出保留范围返回明确错误。Redis 即时广播可用于非关键进度通知，要求重放的结果使用保留的事件日志。任务最终结果独立持久化，不能只存在于连接中。

WebSocket 用于确有双向数据需求的音视频等入口；普通流式文本默认 SSE。实时会话状态隔离和最大持续时间由对应算法声明。

**11. 启停、重载、重启和资源保留**

入口状态为 stopped、starting、ready、reloading、stopping、failed。任务状态与入口状态分开。ready 必须表示路由实际可以接收执行任务。

Reload 的默认流程：读取并校验本次配置 → 在可用资源下初始化新 Graph → 预热 → 切换新请求 → 排空旧请求 → 释放旧 Graph。失败保留原入口及其调用配置。任务接受时固定其配置校验值和执行归属，已排队和执行中的旧任务继续使用原 Graph；新旧实例使用同一个公开名称。旧任务全部终结前保留所需配置和资源。为限制资源占用，同一入口上一轮重载未完成排空时不接受下一轮重载，返回可重试的冲突状态。

启动配置提交与运行切换采用可恢复的顺序，并保留单份上一次可用配置直到切换确认。内部可使用校验摘要、执行序号和原子替换文件，不暴露为版本管理产品。并发 Start/Reload/Stop 对同一入口串行化；重复停止等待同一次释放，不能重复释放原生资源。

新旧模型无法同时装入内存时，预检查失败并明确说明；用户可以显式选择停机重载。不得自动先关闭旧模型，再声称失败保留原服务。

默认 managed 资源策略：

- 保存正在运行的 workflow.json 和 workflow.server.json 的独立副本，草稿变化不影响当前内容。
- 引用已受管理文件，保留其文件 ID 和校验信息；外部本地资源导入 Storage 后由运行配置引用。
- 用户无需逐项创建资源映射。已知模型/文件字段自动识别，自定义节点需声明依赖。
- 删除编辑草稿或外部原文件不删除运行配置及其受管理依赖；引用中的文件禁止普通删除，释放最后一个引用后才允许清理。
- 只承诺已声明的资源完整性，自定义代码私自读取其他路径不能获得同样保证。

可选 reference 策略直接使用用户路径，适合巨大模型或开发场景，但不保证源文件删除后可重建。必须显式配置，页面和状态接口显示该限制。

对象存储文件使用不覆盖的对象 key 或经验证的对象版本引用，并记录内容校验值；ETag 不统一当作内容哈希。下载到 Worker 本地缓存后验证，写临时文件再原子完成，Graph 获取本地路径。缓存正在使用时禁止清理。

重启只恢复已确认可用且 restore_on_restart=true 的入口。未完成的 Reload 不自动替换上次可用配置。代码入口需要可导入工厂和可用依赖；临时闭包或仅存在于内存中的 Graph 不承诺跨进程重启恢复。

崩溃时未确定完成的任务标记失败或等待人工处理。只有算法明确声明可重试且资源输入已保留时才自动重试；模型恢复与任务自动重跑是不同操作。

**12. 数据库与数据模型**

采用统一的关系数据库访问实现，建议使用 SQLAlchemy 管理方言、连接和事务，Alembic 管理迁移；驱动按后端选装。SQLAlchemy 列出 SQLite、MySQL、PostgreSQL 方言，Alembic 提供数据库迁移工具；这不替代本项目自身的兼容测试。[SQLAlchemy 方言](https://docs.sqlalchemy.org/en/20/dialects/)、[Alembic](https://alembic.sqlalchemy.org/en/latest/)

业务层直接调用 DB 的明确方法，暂不叠加通用 Store/Repository 层。保留 `from .db import DB` 的兼容导出，内部将现有 db.py 迁入 db/。

| 数据 | 用途与关键内容 |
| --- | --- |
| workflows、templates | 现有 ID、名称、位置、封面、说明及时间，保持兼容 |
| tasks | task_id、入口名、可选 workflow_id、身份、状态、时间、期限、输入引用、结果引用、错误、幂等键、执行归属 |
| files | file_id、后端、对象 key、本地位置、类型、大小、校验、权限归属、生命周期状态 |
| server_configs | 每个公开名称的一份已确认配置、来源、受管理资源引用、恢复意图和配置修改校验值；不保存发布历史 |
| task_events（按需） | 需要持久化的审计或事件；高频流式事件可按保留策略放 Redis/文件 |
| 访问凭据/审计数据 | 本地 API key 启用时保存密钥摘要、作用域、撤销状态；不重复构建完整用户系统 |

文件引用关系必须可查询，可用关联表实现；不能仅以易失引用计数决定是否删除。任务和当前运行配置都可能持有文件。任务还保存接受时的配置校验值和内部执行序号，用于排队期间重载和迟到结果判断；这些字段不是对外版本对象。

执行状态更新采用事务和条件更新。连接按请求/操作管理，禁止多个线程无保护地共用一个 sqlite3 连接。SQLite 使用适合本地的并发设置；MySQL/PostgreSQL 使用连接池和断线检测。SQL 不依赖某一方言特有的 JSON 查询、自动增长或锁语法来保证通用正确性，差异封装在 DB 内。

接口：get_workflow、save_workflow、create_task、claim_task、finish_task、get_task、create_file、get_file、save_server_config 等，使用领域已有名称。数据库事务不跨越整个模型执行或云文件上传。

有状态任务必须先可靠落库再接受执行。输入正文默认不记入普通日志；需要异步执行和恢复的数据存入受控任务内容或文件引用，并配置保留时间。不可恢复模式明确标记。数据库不可用时，要求记录的入口拒绝新请求，不先执行后假装记录成功。

迁移要求：保留现有工作流 ID 与文件位置；迁移可重复检测；升级前备份；数据库升级只由受控迁移过程执行，多实例不能同时自动改表。跨 SQLite/MySQL/PG 迁移另提供导入导出校验，不宣称修改 URL 就能搬迁现有数据。

**13. 文件与对象存储**

files.py 负责业务：授权、上传/下载协议、元数据和文件生命周期。storage/ 负责字节内容：put、open、stat、delete、download_to、signed_url。云 SDK 只在对应驱动中按需导入。

| 后端 | 支持要求 |
| --- | --- |
| Local | 安全路径、原子写入、流式读写、清理、校验 |
| S3 / 验证过的兼容存储 | 上传下载、分片、校验、签名访问、异常重试、兼容测试 |
| 腾讯 COS | 厂商驱动，验证凭据、地域、分片、签名地址及错误转换 |
| 阿里 OSS | 厂商驱动，验证同一组公共行为和特有能力 |
| 华为 OBS | 厂商驱动，验证同一组公共行为和特有能力 |

厂商差异不泄漏给算法，但不支持的操作必须明确返回。不能只将 endpoint 改成任意地址就宣称支持所有对象存储。S3 的分片上传、完成及中止需要管理上传生命周期，未完成分片须清理。[S3 分片上传](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)

COS、OSS 使用各自官方 Python SDK 作为实现依据，并锁定测试通过的依赖组合，不把文档示例中的凭据写进代码。[COS Python SDK](https://cloud.tencent.com/document/product/436/12269)、[OSS Python SDK](https://help.aliyun.com/zh/oss/developer-reference/2-0-manual-preview-version/)

上传过程采用临时状态：校验配额与声明 → 写入内容 → 验证实际大小/类型/校验值 → 提交可用文件记录。内容写入成功但 DB 失败时清理内容；无法立即清理的孤立文件由后台对账回收。输出文件同理：只有结果记录提交后才成为成功交付的结果。

大文件可由客户端直传对象存储，但必须由 Server 发放受限上传授权并在完成时验证；未验证前不能作为 Graph 输入。签名 URL 按权限和用途生成，短期有效，不作为长期地址写入 DB。

文件访问默认通过 file_id，禁止外部调用者指定任意服务器路径。支持输入目录、临时目录和结果目录隔离。删除检查身份及运行/任务引用；清理任务不能删除排队任务或运行 Graph 所需文件。

远程资源下载限制来源和访问范围，不让普通 Deploy 请求变成任意 URL 下载器。针对视频、音频、图片和压缩内容，除传输大小外还限制解码后的资源消耗。

**14. Redis、分布式任务与一致性**

Redis 是可选的缓存和协调设施，不是唯一业务事实来源。单机默认使用每入口独立的本地 TaskQueue；启用共享队列时使用相同的任务接口。共享表示同一入口可被多个 Worker 消费，不表示所有模型混在一个全局 FIFO 中。默认按部署命名空间和入口名划分队列/Stream，只有匹配的 Worker 才能领取；需要物理复用时也必须保持同等的路由、容量和公平性。

任务队列建议基于 Redis Streams 消费组，保留确认和待处理消息恢复机制。Redis 的 XREADGROUP 记录未确认消息，XACK 确认消费；应用仍需处理重复交付和数据库一致性。[XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/)、[XACK](https://redis.io/docs/latest/commands/xack/)

提交与执行步骤：

1. 在 DB 保存 pending 任务、幂等键、输入引用和有效期限。
2. 将 task_id 投递到 Redis；投递失败保留可补发状态，由后台扫描补发。
3. Worker 收到消息后，在 DB 条件领取任务，获得执行归属和内部执行序号。
4. 领取失败或已终态的重复消息直接按规则确认；过期任务不执行。
5. 执行完成，以相同归属/序号条件提交结果，再确认队列消息。
6. 结果已提交但确认丢失时，重复消息看到终态，不重新执行。

心跳或租约超时不能证明原计算已经停止。迟到 Worker 的结果通过归属检查拒绝覆盖；有外部副作用的算法还需要自身幂等或明确不自动重试。系统不承诺通用 exactly-once 计算。

Redis 还用于限流、短期缓存、Worker 心跳、事件分发。锁必须有所有者和过期策略，但锁不是数据库事务的替代品。模型和大型媒体不直接存入 Redis。

故障策略按用途定义：缓存不可用可以回源；共享队列不可用停止接受无法保证投递的新任务或明确返回已持久化待调度状态；安全限流不可用默认拒绝受保护请求。不得静默切换到每个实例各自的本地队列，造成重复执行。

Redis 和 DB 恢复后进行任务及事件对账。扫描和回收有时间、数量边界。集群命名空间、连接池、认证/TLS、超时和重连均可配置。

同一入口的 Start/Reload/Stop 在多实例中由一个有执行归属的控制者协调，并以 DB 条件更新最终提交，不能只依靠进程内锁。仅将相同配置且已就绪的 Worker 纳入当前调度集合。切换不要求所有机器同时完成，而是只向已经确认的集合派发新任务；旧集合处理固定归属的旧任务。API 实例的本地状态缓存失效时重新核对，不能派发到过期配置。Redis 连接恢复或控制者更换后，迟到的控制消息必须通过内部执行序号被拒绝。

**15. HTTP 协议与身份标识**

保留现有 `/api/workflow`、`/api/queue`、文件与 WebSocket 接口的兼容行为。新调用协议独立定义，不能直接改变老前端的响应结构。

| 方法与路径 | 功能 |
| --- | --- |
| GET `/health/live` | 进程存活，避免重型依赖探测 |
| GET `/health/ready` | 必要依赖和配置为必需的入口可用 |
| GET `/v1/models` | 当前允许调用的入口、显示名和能力，兼容算法协议需要 |
| GET `/v1/server/{name}/schema` | 所有入口的通用 schema 与能力 |
| POST `/v1/server/{name}/deploy` | 同步、异步或流式执行 |
| GET `/v1/tasks/{task_id}` | 状态和最终结果引用 |
| POST `/v1/tasks/{task_id}/cancel` | 申请取消，返回实际状态 |
| GET `/v1/tasks/{task_id}/events` | 经授权的事件流 |
| POST `/v1/files` | 上传文件 |
| GET `/v1/files/{file_id}` | 文件元数据 |
| GET `/v1/files/{file_id}/content` | 下载或受控跳转签名 URL |
| DELETE `/v1/files/{file_id}` | 在权限和引用允许时删除 |
| POST `/api/server/{name}/start` | 管理操作，加载工作流或已注册代码入口 |
| POST `/api/server/{name}/reload` | 管理操作，安全应用新配置 |
| POST `/api/server/{name}/stop` | 管理操作，排空并停止 |
| GET `/api/server`、`/api/server/{name}` | 入口列表和运行状态 |
| GET `/metrics` | 受保护的运行指标 |

`/v1/server/{name}/schema` 统一描述 Graph 和代码入口，不另建同义接口。模型列表描述可调用能力，不假定一个 Graph 只有一个权重模型。

通用请求示例：

```json
{
  "inputs": {"image": {"file_id": "file_example"}},
  "parameters": {},
  "mode": "sync"
}
```

mode 为 sync、async 或 stream，只有入口声明支持的方式可以使用；可选调用期限受 Server 上限约束。流式模式需要一致的 Accept 和响应类型。专用算法协议可以使用自己的请求结构，但转换后进入同一执行路径。

同步成功返回 200 和 task_id、outputs；异步或尚未完成的控制操作返回 202 和查询位置。排队满/配额不足返回 429，未就绪/必要依赖不可用返回 503，输入错误返回 422，内容冲突返回 409，权限错误为 401/403，文件过大为 413，支持的同步等待超时返回明确的 504 和已接受任务标识。

统一错误结构包含 code、message、可选 field、task_id/request_id 和 retryable。内部堆栈、凭据和任意本地路径不直接暴露。

Start、Reload 和可重试 Deploy 支持 Idempotency-Key，按身份和入口限定作用域，保存请求摘要及原结果。同键不同内容返回 409。启动响应丢失时重试不能再创建一个并行模型。幂等保留期限对外说明，过期后不保证去重。

**17. 安全、监控与非功能要求**

API-only 默认不挂载工作流上传、Python 插件上传、模板和调试接口。管理接口与调用接口分别授权。支持本地 API key，并预留与现有身份系统验证结果对接的依赖；权限至少覆盖入口调用、任务查看/取消、文件读写和运行管理。

每个文件、任务和入口操作检查身份范围，不能仅依赖 ID 难猜。CORS 来源明确配置；生产启动时不使用任意来源加凭据的默认组合。TLS 可以由入口代理终止，但代理身份和转发头必须限定可信来源。

请求大小、文件大小、解码资源、队列、并发、连接数、流式持续时间和磁盘容量有上限。秘密值只从环境或凭据设施读取，DB/API key 使用摘要存储，日志脱敏。

日志关联 task_id、HTTP request_id、入口和 Worker。状态和指标按入口展示排队数、在途数、就绪 Worker、设备放置、限额和拒绝原因；汇总指标不能遮蔽某个入口的拥塞。指标包含排队/初始化/执行/上传下载耗时、任务状态、请求错误、队列长度、在途数量、文件清理失败、DB/Redis/Storage 延迟。指标标签不使用无界 task_id 或原始用户输入。

健康检查区分进程活着和入口可接受请求。一个可选入口失败不必让整个应用不就绪；必需入口和依赖的策略可配置，返回结果不得泄露秘密信息。

非功能验收：无阻塞计算占用 HTTP 事件循环；指定并发下内存/队列有界；重复调用和失败恢复不持续泄漏；平台支持范围明确。性能不预先编造 QPS，建立相同机器、模型、输入的基线，分别记录 p50/p95/p99、首包/首 Token、吞吐和资源占用。

**20. 故障处理和降级要求**

| 故障 | 必须表现 |
| --- | --- |
| DB 在提交前不可用 | 拒绝需要持久化的新任务，不执行模型 |
| DB 在结果提交时失败 | 不返回成功；处理已生成文件，保留可对账信息 |
| 云存储下载失败 | 未就绪或任务失败，禁止传递半文件给 Graph |
| 输出上传失败 | 任务失败；清理部分上传和本地临时结果 |
| Redis 缓存失败 | 在允许范围回源，记录降级 |
| Redis 队列失败 | 不悄悄改成本地独立执行；已落库任务按策略等待补发 |
| Worker 崩溃 | 入口不可用/恢复中；标记受影响任务，恢复模型；独立 Worker 的其他入口继续工作 |
| 单入口过载 | 该入口背压；不占住其他入口执行通道，应用总量限额仍生效 |
| 共享 GPU 资源不足 | 对相应启动/请求给出明确结果，不通过静默停止其他模型释放资源 |
| 客户端断开 | 执行归属继续有效，按声明策略继续或取消 |
| 新模型显存不足 | 保留旧入口，明确重载失败 |
| Server 在切换中退出 | 重启读取最后确认的配置，处理残留临时文件 |
| 凭据失效 | 返回明确认证/依赖错误，不打印秘密值 |
| 清理失败 | 可重试、可观测，不误删被引用的资源 |

安全的最小基线、容量限制、日志和健康检查从 A/B 开始落地，F 是补齐，不是此前裸露上线的理由。各阶段可评审和使用，但完成 B 不能宣称完整 Server 已完成。

数据库、对象存储和 Redis 的测试不能只用 mock 代替。云厂商账号缺失时可完成本地实现和公共接口测试，但对应后端必须标记未验证，不能计为支持完成。

最低验收矩阵：

- 接入：工作流 JSON、直接 Graph、Graph 工厂、同步函数、异步函数、常驻对象、流式生成器。
- 调用：同步、异步、流式、显式批量；动态合批只在声明入口验证。
- 存储：SQLite/MySQL/PG × 公共 DB 用例；Local/S3/COS/OSS/OBS × 公共存储用例。
- 部署：单机无 Redis；Redis 单机多进程；共享 DB/Storage 的多节点 Worker。
- 媒体：文本/JSON、图片、音频、视频、文件、数组/Tensor；包含无效和超限输入。
- 可靠性：连续调用、并发隔离、取消、超时、Worker 崩溃、重载失败、重启恢复、输入/输出清理、重复投递。
- 安全：调用、管理、文件、任务权限；不可信路径和 URL；大小限制；日志脱敏。
- 编辑器：Start 一次操作完成，Ready 后可调用，Reload 失败旧接口可用，保存不修改在线配置，Stop 可观察排空状态。

多模型调度必须增加以下独立验收用例：

| 编号 | 场景 | 必须验证的结果 |
| --- | --- | --- |
| Q01 | A 使用阻塞测试执行器，B 是短任务，各自独立 Worker | 在未命中总量/设备限制时，B 在 A 释放前完成；用同步屏障验证，不依赖偶然耗时 |
| Q02 | A 的待执行队列已满，B 仍有容量 | A 返回 429，B 可接受和执行；不会先把 A 放进无界下游队列 |
| Q03 | 同一 Graph 同时收到两个请求 | 默认不重叠执行，输入默认值和输出不串扰 |
| Q04 | 同一入口配置两个 Worker | 两个独立 Graph 可以重叠执行，模型内存按实际实例计入 |
| Q05 | engine 模式接入可多请求的算法 | 首个流式任务未结束时第二个可以被引擎接受；总在途上限有效 |
| Q06 | 同机两个独立 Server 进程 | 不共享任务队列和控制操作；停止 A 不停止 B |
| Q07 | A 重载失败或所属 Worker 崩溃 | B 的路由、队列和 Worker 保持可用；A 按规定恢复 |
| Q08 | 多入口共享总量或设备限额 | 总量不超限，有保留配额的入口不会被其他入口用尽容量；等待不持有阻塞全局的锁 |
| Q09 | Redis 同组多 Worker、多个入口 | 同名同配置 Worker 共享对应入口任务；不同名称/命名空间不误领任务 |
| Q10 | 资源协调租约过期但计算仍在运行 | 不提前释放名额，不让迟到结果覆盖新归属；核实结束后正确回收 |
| Q11 | CPU、不同 GPU、同 GPU 三种放置 | 前两者没有人为全局串行；共享 GPU 记录真实性能和资源影响，不承诺硬件隔离 |
| Q12 | 非受管进程占用 GPU 或新旧模型同时装入失败 | 明确返回资源失败并保留原入口，不自动关闭其他模型 |

Q01–Q10 先用受控执行器验证调度正确性，再以真实 Graph/引擎验证对应能力。Q11–Q12 需要真实设备环境；缺少设备时标记未验证，不用 CPU mock 宣称 GPU 验收通过。

交付物包括：可运行代码、数据库迁移、配置示例、Graph/代码/多媒体样例、编辑器页面、CLI 帮助、依赖分组、启动和故障恢复说明、API 文档、后端兼容矩阵、测试与基准报告。

本文件仅确定需求和设计，不承诺这些功能已在当前分支实现。实现过程中的依赖版本、超时和容量默认值应在目标环境中验证并记录；改变协议、运行所有权或数据保留语义时，需要同步更新本文件及验收用例。
